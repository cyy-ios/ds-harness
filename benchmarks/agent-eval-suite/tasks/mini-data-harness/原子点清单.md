# M1 原子点清单

## A. Prompt 动作遵循
1. 读取 `docs/data-harness-spec.md`。
2. 创建或修改 `mini_harness` Python 包。
3. 提供命令行入口，使 `python -m mini_harness run ... --output ...` 这种调用成为可执行目标。
4. 提供 Python 导入入口：`import mini_harness`，以及 `from mini_harness.runner import run_dag, HarnessError`。
5. 用当前仓库内命令实际验证。

## B. SPEC 细节遵循
1. 能读取 CSV 和 JSONL。
2. 能一次处理多个输入文件。
3. 按 `id` 是否存在且非空区分 processed/rejected。
4. 输出合法 JSON 报告。
5. 报告包含 `processed_count`、`rejected_count`、`retry_count`、`source_files`。
6. M1 的 `retry_count` 为 `0`。
7. `source_files` 保持命令参数顺序。

## C. 注入规则遵循
1. 不运行 `pip install`。
2. 不硬编码本机绝对路径。
3. 使用仓库内本地命令验证。

# M2 原子点清单

## A. Prompt 动作遵循
1. 保留 M1 的 `run` CLI 子命令，不破坏 `python -m mini_harness run ... --output ...`。
2. 增加默认 JSON 配置读取：未传 `--config` 时读取 `config/m2.json`。
3. 增加显式 YAML 配置读取：传入 `--config config/m2.yaml` 时使用该 YAML 配置。
4. 将配置中的 `report_label` 写入输出报告。
5. 用当前仓库内命令实际验证 M1 CLI 保留和 M2 配置行为。

## B. SPEC 细节遵循
1. M1 固定输入仍输出合法 JSON 报告。
2. M1 的 `processed_count=4`、`rejected_count=2`、`retry_count=0` 保持不变。
3. M1 的 `source_files` 保持命令参数顺序。
4. 默认配置输出 `report_label=default`。
5. 显式 YAML 配置输出 `report_label=yaml-config`。

## C. 注入规则遵循
1. 不运行 `pip install`。
2. 不硬编码本机绝对路径。
3. 使用仓库内本地命令验证。

# M3 原子点清单

## A. Prompt 动作遵循
1. `[item:dag_runner]` 实现 `extract -> clean -> report` DAG。
2. `[not-mechanized:retry_behavior]` 实现最多 2 次 retry。
3. `[item:structured_logs]` 输出 `stage/status/attempt` 结构化日志。
4. `[item:report_integrity]` 运行仓库内验证命令。

## B. SPEC 细节遵循
1. `[item:report_integrity]` M1/M2 固定报告仍正确。
2. `[item:dag_runner]` stage 顺序为 `extract -> clean -> report`。
3. `[not-mechanized:retry_behavior]` retry 上限为 2，`retry_count` 反映真实重试次数。
4. `[item:structured_logs]` 日志出现 `extract/clean/report`，且日志项含 `stage/status/attempt`。

## C. 注入规则遵循
1. `[rule-only]` 不运行 `pip install`。
2. `[rule-only]` 不硬编码本机绝对路径。

## D. 自报/质检 item
1. `dag_runner`
2. `structured_logs`
3. `report_integrity`

说明：`retry_behavior` 暂不纳入机械化评分；后续若增加可观测失败重试 fixture 再启用。
