# 实施与验证

## 目标

基于 Codex 构建可日用、可维护、可演进的 DeepSeek V4 原生 agent harness。所有改造按[四层架构](../reference/agent-harness-architecture.md)归类；核心指标为任务成功率、规则遵循率、长程保持率、工具成功率、验证充分率、错误恢复率、压缩后状态保持率、成本和延迟。

## 改造边界

1. 上下文层：适配 DeepSeek 指令、消息组装、长上下文和压缩策略。
2. 工具层：适配 DeepSeek 工具调用，保留 Codex 的参数校验、审批和沙箱边界。
3. Agent Loop 层：保留 Codex 基本循环，按评测改进验证、重试、续跑和终止判定。
4. 状态与运行时层：保留 thread、事件、持久化、恢复、权限和故障处理，避免把运行时职责下沉到 provider。
5. 不以复刻 Codex 或 Claude Code 的模型专用策略为目标。

## 验证流程

1. 建立 20 个固定任务，对 Claude Code+DeepSeek、Codex 基线和候选策略统一评测。
2. 按 provider 边界 → 上下文层 → 工具层 → Agent Loop 层 → 状态与运行时层逐项消融。
3. 每次只改一项；只有产生可重复净增益的机制才进入稳定实现。
4. Trace 记录请求、响应、工具、token、压缩、权限、重试和状态事件。

## 输出契约

- `benchmarks/tasks/`：固定任务与评分规则；稳定输入，不随单次实验修改。
- `benchmarks/baseline/`：当前有效基线与汇总指标；新基线验收后覆盖。
- `docs/decisions/`：已确认的长期决策；只写结论、依据和替代方案。
- `docs/reference/`：稳定分析与源码索引；不写运行日志。
- `internal/runs/<run-id>/`：单次 trace、原始结果、调试证据和中间产物；下游不得依赖。
- `internal/candidates/`：尚未验收的策略和结果；通过评测后才迁入稳定实现或文档。
- `archive/`：被替代但需追溯的历史基线；不作为默认输入。

稳定文档和基线必须注明对应代码版本、模型、参数和任务集版本；过程证据不得写入 README、决策或参考文档。

## 失败去向

- 环境、接口或工具故障：记录到对应 `internal/runs/<run-id>/`，修复后重跑，不计入策略结论。
- 策略未达到阈值：保留在 `internal/candidates/` 或删除，不进入稳定实现。
- 出现安全、数据损坏或不可恢复回归：立即停止迁入，恢复当前基线并记录决策。

## 完成标准

候选版本须在同模型、参数、预算和任务集下重复评测至少 3 次；核心任务成功率相对当前 Claude Code+DeepSeek 基线有可重复提升，规则保持率和错误恢复率不得下降，安全/恢复/持久化回归测试全部通过，成本与延迟变化已记录。具体晋升阈值在首个稳定基线建立后写入任务评分规则。
